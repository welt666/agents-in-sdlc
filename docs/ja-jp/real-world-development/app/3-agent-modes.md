プロジェクトに小さな機能を追加しました。より大きな変更には、さらにしっかりとしたプロセスが必要です。GitHub Copilot app は組織の既存のワークフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント駆動型開発のプロセスを実践します。issue から新機能を作成し、コードが正しく、機能が期待どおりに動作することを確認して、最終的にプロジェクトにマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使います。通常はファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主な概念に集中できるように手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue から新しいエージェントセッションを始めます。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続ける間に、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増えてきたため、訪問者がカテゴリや出版社でゲームを絞り込めるようにします。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細もあります。Plan モードで判断を確定し、Autopilot には範囲を限定した実装を許可します。

## 背景

AI コーディングエージェントを開発ワークフローに導入しても、基本は変わりません。むしろ、基本がさらに重要になります。多くの開発者は、次のような手順で作業します。

1. 実施する作業が詳しく書かれた issue を開きます。
2. 実装する内容の計画を作成します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものです。

標準的な手順を守ることで、AI が生成したコードが要件を満たし、手作業で作成したコードと同じレビューを受けるようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行する前にユーザーの入力を待ちます。
- **Plan**: エージェントが計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律して作業し、入力を待たずにコード作成、テスト実行、反復を行います。

まず Plan モードで計画を確認し、その後 Autopilot モードで実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。テンプレートに含まれる既存の issue なので、新しい issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。issue から開始したため、Copilot は機能の依頼をコンテキストとしてすでに把握しています。次の内容を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ条件と計画を比較します。カテゴリと出版社による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれることを確認します。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。計画に変更が必要な場合は、承認前に依頼します。後で検証できるよう、issue の URL と合意した追加の決定事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認しただけでモードが自動的に切り替わると思い込まず、アクティブなモードを確認してください。モード表示が **Autopilot** であることを確かめます。

Copilot が実装を開始します。作成した計画に沿ってコードを生成し、テストを実行しながら、プロセスを反復して進めます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同様にマージ前にレビューします。コードをレビューし、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと出版社の組み合わせも含め、結果を issue と承認した追加の決定事項に照らし合わせます。変更が既存のリポジトリの指示に沿っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、影響を受けるチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用する場合があります。以前のレッスンではなく、この worktree で実行されているサーバーをテストしていることを確認します。

## 新機能を試す

コードに問題がないことを確認したら、アプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターをクリアしてから出版社を選択し、結果が一致することを確認します。
4. カテゴリと出版社のフィルターを組み合わせ、結果を issue と承認した計画に照らし合わせます。複数カテゴリに対応している場合は、合意した組み合わせの動作も確認します。
5. ゲームが見つからない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、全ゲームが再び表示されることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

フィルター機能の PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はフィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後、セッションをそのままにしてもかまいません。次のレッスンで同じセッションに戻ります。
